## 1. 為什麼做、給誰

DDIA 很厚，但 technical PM 需要的不是儲存引擎或共識演算法的內部，而是：哪些需求要寫進 spec、工程方案的取捨、該問工程師什麼、使用者會碰到什麼異常。篩選已經做完；這個網站把結果變成兩樣東西：

1. **地圖與主題頁**：一眼看出 PM 該懂哪些主題、屬於 PM 的哪件工作，點進去是結論、取捨、該問工程師的問題與例子。
2. **互動實驗**：讀者親手做出使用者會碰到的失敗（重複下單、存了卻不見、兩人互相覆蓋），再看修法怎麼擋住。

讀者是想轉 technical PM 的工程師，或想懂技術的 PM，產品型與平台／資料型都要照顧；不需要會寫後端。讀繁體中文或英文。

## 2. 界線

**這版不做**

- 篩選版「其餘要能問」的一行版段落與「只要懂名詞」的段落（索引裡標「一行版」「不收」）；一行版要不要收見第 10 節第 1 項（收的話，每章一頁列表）。地圖頁首說明本站只收 PM 篩選後的段落。
- 帳號、進度同步、留言、搜尋。實驗課進度只存在網址與瀏覽器本機（同 C++ lab）。
- 角色篩選（產品型／平台型）：兩種角色的評級差別，幾乎正好落在第一線和第二線的分界上，地圖分兩區就已經表達出來，篩選不會再多告訴讀者什麼；評級經實務校正、出現新的差異時再考慮。

**做了就算失敗**

- 變成書的摘要或替代品（第 8 節）。
- 該翻譯的文字沒翻，或兩種語言講的內容不一樣（6.2、6.4）。
- 為了好看而加的圖（C++ lab 的規則）。視覺化集中在地圖與實驗課，主題頁不強制配圖。

## 3. 內容與資料模型

**結構**（不含要逐語言翻譯的文字）：

- `src/content/sections.ts`：由 `scripts/build-content-index.mjs` 產生，不手改，以 `as const` 輸出。每段一筆：`id`、所屬主題、章、書中英文標題與中文名、印刷頁碼、兩種角色的評級。頁碼與評級因此不會手抄出錯。
  - **`id`**：「章號＋英文 slug」，例如 `ch9-unreliable-networks`。slug 取自書中英文標題；沒有書中標題的段落（只有中文標題），在產生器的覆寫清單裡手寫一個英文 slug。不用行號，筆記改動不會讓已寫好的文字對不上；`id` 重複時產生器失敗。每個段落區塊在頁面上帶 `id=<段落 id>`，測試與人工核對都用它；階段 1 起 `content-index.md` 也印出這個 id。
  - **頁碼**：筆記寫 PDF 頁碼，書上印的頁碼＝PDF 頁 − 24。網站一律顯示印刷頁碼；`content-index.md` 與兩份設計稿用 PDF 頁碼，對照筆記用。
  - **書中標題**：筆記標題括號外沒有中文字，就是書中英文標題，括號裡是中文名。收錄的 89 段裡，括號外有中文、又帶英文的 7 個已對照原書確認（2026-10-24）：6 個是書中標題，由產生器內的覆寫清單給出（PDF p.203、207、210、214、304、307）；「Replication and Backups」不是（書中是 Backups and Replication，p.222），當作沒有書中標題。其他沒有書中標題的段落（「怎麼選（判準）」「章首」等）用我們寫的標題並標「整理自本章」。一行版若之後要收，同樣的人工確認還有約 30 個。
- `src/content/structure.ts`：手寫。`topics` 依地圖順序列出每個主題 `{ id, zone, group?, phase }`（第二線沒有 group），型別保證每個 `TopicId` 恰好出現一次，漏寫或多寫一個就 typecheck 失敗；上一個／下一個照這個順序。`labs` 是 `Record<LabId, { topics, phase }>`，實驗的階段只寫一處。

產生器讀 `~/.claude/memories`，只能在 Debra 的電腦上跑；筆記或篩選版改了要重跑並提交。它用「章＋標題」把篩選版每筆條目對到筆記的一個段落；條目解析不出來（另以「結論」行數核對）、對不上、重複，或同一段被兩個主題收錄，都會讓產生器失敗（現已如此）。`--check` 只比對提交的檔案是否過期（`content-index.md` 已支援，`sections.ts` 階段 1 加上）；一個 vitest 在本機有 `~/.claude/memories` 時跑 `--check`，沒有時跳過。

**文字**（`src/content/zh-TW/`、`src/content/en/`，用段落 `id` 對應）：每個主題的標題與一句話摘要；每段的結論、取捨、該問工程師的問題、例子，以及沒有書中標題時我們寫的標題。每個例子旁標來源 `'book' | 'ours'`（兩種語言一致由型別保證，見 6.4）。

- **例子**：篩選版有 24 段的例子取自 Debra 的工作，一律刪掉，不改寫：T0 Systems of Record；T3、T4 各三段；T5 Reading your own writes；T6 Dealing with Conflicting Writes；T7 四段；T8 第 13 章怎麼選；T9 兩段；T10 三段；T11 Sharding for Multitenancy；Q2 Microservices and Serverless；Q6 Storage and Indexing for OLTP；Q14 第 11 章章首；Q15 Stream Joins（逐段列出，因為有幾個例子沒寫系統名稱，搜不到）。刪掉後：T3、T4 改用 D1 的「送出訂單」情境，讓主題頁和實驗用同一套詞；其他段落若沒有剩下的例子，就用筆記裡該段的書中例子，不另編情境。另外 3 個「筆記補充」不是取自 Debra 的工作：T2 的 63% 算例與 Q3 的重試風暴照常保留，標「補充（非書中）」；T12 那個其實是書中第 12 章的說法（PDF p.536–537），標「書中」。
- **內文裡的頁碼**：一律寫成 PDF 頁碼的標記（例如 `{p:372}`），由同一個格式化函式換成印刷頁碼；測試掃內容檔，出現直接寫的頁碼（`p.348`、`p. 348`、`page 348`、`第 348 頁`）就失敗。

## 6. 多語言

### 6.1 網址與切換

- 兩種語言：繁體中文 `zh-TW`（內容先寫這版）與英文 `en`；不打算再加其他語言（Debra 2026-10-24 決定）。兩種都完整才上線，沒有「缺的先顯示另一種語言」的退路。
- 語言放在網址路徑：`/zh-TW/…`、`/en/…`；分享出去的連結一定帶語言。
- 建置時為每種語言、每個已上線的路徑預先產生 HTML（還沒上線的不產生）；另產生 `404.html`（5.4），`base` 路徑可設定；這樣 GitHub Pages、Netlify、Cloudflare Pages 都能直接放，重新整理任何一頁都不會 404。
- 進入根路徑 `/`：讀者手動切換過就用那個語言（記在本機，讀寫包 try/catch）；否則看瀏覽器語言，`zh` 開頭的導到 `zh-TW`，其餘導到 `en`。根路徑的頁面本身也列出兩種語言的連結，導向失敗時讀者自己點。
- 每頁都有語言切換，切換後停在同一頁的另一語言版本；切換鈕上的語言名稱用該語言本身寫（「繁體中文」「English」）並標 `lang`；實驗課的進度（網址上的事件序列）跟著保留。`<html lang>` 隨語言切換。

### 6.2 文字放哪裡

- 元件裡不寫任何文字：介面文字、主題內容、實驗課的題目與回饋放在 `src/content/<語言>/`；刻意不翻的文字（書中英文標題、術語原文、程式碼、數字與頁碼）也來自 `sections.ts`、`examples/` 或內容檔。
- 和 C++ lab 不同：那邊的 `tasks`、`guides` 寫在 `*Workshop.ts`；這裡模型（`simulate`、`enumerateOrderings`、`replay`）只回傳代碼與數值，畫面依代碼查字典。
- 有插值的句子（例如「訂單有 {count} 筆」）用具名參數，讓兩種語言的語序各自調整；數字、百分比用 `Intl` 依語言格式化。
- 程式碼面板的 SQL 與 API 片段兩種語言共用一份（仍從 `examples/*.sql` 切出），旁邊的說明才翻譯。

### 6.3 術語

- 一份給寫內容的人看的術語表（`docs/glossary.md`，不在網站上顯示）：每個術語的中文、英文（照書中用字）。中文版在每個段落區塊或每一題裡第一次出現時寫「複製延遲（replication lag）」，之後只寫中文（由寫內容的人照做，不另寫測試；讀者可能直接進任何一頁、展開任何一塊）；PM 從工程師那裡聽到的常是英文。
- 同一語言內，題目、時間軸、試跑表、回饋用同一組詞（C++ lab 的「一套詞彙」規則）。

### 6.4 用測試守住

- **key 對應**：`zh-TW` 的段落文字型別是 `Record<SectionId, …>`（`SectionId` 取自 `sections.ts`），`en` 的型別由 `zh-TW` 推導；缺 key、多 key、例子數量或來源不一致，typecheck 就失敗。
- **元件裡沒有寫死的文字**：測試用一個假語言渲染元件，假語言把每個來自資料的字串（含刻意不翻的那些，以及經 `Intl` 格式化的數字）包上記號（例如 `⟦…⟧`）；畫面上的可見文字、`aria-label`、`alt`、`title` 與頁面標題，出現沒包記號的就失敗。
- **英文版沒有中文**：`src/content/en/` 與建置出的英文頁面（含上述屬性與頁面標題）出現中文字就失敗；標了 `lang="zh-TW"` 的元素（語言切換鈕、雙語找不到頁）除外。
- **連結都通**：對建置好的 `dist` 開一個像 GitHub Pages 的靜態伺服器（不存在的網址回傳 `404.html`、狀態碼 404），從根路徑 `/` 出發，在兩種語言下跟著每個站內連結走，每個網址都直接載入（模擬重新整理）；任何一個回 404 就失敗。每個載入的頁面都跑 axe；走到的主題頁必須正好等於 `structure.ts` 裡已上線的主題（地圖漏列一個就失敗），每個主題頁都要找得到該主題每一段的區塊；每頁的語言切換連結必須指向另一語言的同一路徑。這同時驗證「每個階段單獨上線」與「重新整理不會 404」。另直接打開一個多層的錯誤網址（例如 `/en/topics/x/y`），確認得到 404 和站內找不到頁，並跟著頁上兩個連結都回得到地圖；所以站內連結一律寫成含 `base` 的絕對路徑，不用相對路徑。
- **實驗課**：Playwright 在兩種語言下走每個實驗課的每一題，含 axe。

### 6.5 翻譯流程

先寫 `zh-TW`（來源是中文筆記），再寫 `en`；英文版的術語與標題照書中原文。兩種語言由 Claude 寫、Debra 審（Debra 的母語是英文，英文版不另找人審），同一次改動同時更新兩種。測試擋得住缺漏、擋不住意思不同，所以審稿時兩種語言並排看。

## 7. 技術與結構

技術同 C++ lab（另在 `package.json` 的 `engines` 要求 Node ≥ 22.13，`node:sqlite` 需要）：Vite、React、TypeScript、vitest、Playwright、axe，套件版本照抄 C++ lab 的 `package.json`（該版 vitest 載入不了 `import 'node:sqlite'`，D1 的 SQL 測試改用 `process.getBuiltinModule('node:sqlite')`，已驗證可用）；路由、預先產生 HTML、i18n 能用小段自己的程式就不加套件。

```
src/
  content/sections.ts           # 產生器輸出：段落 id、書中標題、印刷頁碼、評級
  content/structure.ts          # 手寫：分組、階段、實驗對應
  content/zh-TW/                # 主題文字、介面文字、labs/d1.ts …
  content/en/
  i18n/                         # 語言清單、偵測、切換、查字典
  lessons/<name>Workshop.ts     # 實驗模型，不含文字
  components/
examples/<name>.sql             # 實驗課的可執行證據（node:sqlite）
scripts/build-content-index.mjs # 產生 docs/content-index.md 與 src/content/sections.ts
e2e/
docs/
```

本 repo 要有自己的 `CLAUDE.md`：照抄 C++ lab 的流程規則（一次一課、先寫失敗的測試、每次改動跑 `pnpm test && pnpm build && pnpm test:e2e`、截圖檢查、沒說 commit 就不 commit；截圖要兩種語言、手機 375px 與桌面各一張，看英文較長時版面有沒有斷開），再加上第 6 節與第 8 節的規則。

## 8. 公開前的規則

適用於網站，也適用於整個 repo（文件、範例、提交紀錄），因為放上 GitHub Pages 通常代表 repo 公開。

- 書的內容用自己的話寫；引用只用短句並附頁碼。
- 不出現 Debra 工作上的公司、客戶、系統，或取自 Debra 工作的情境（3 節「例子」）。
- 提交者身分：第一次提交前，在這個 repo 設定本地的 `user.email` 為 GitHub 的 noreply 位址（全域設定是工作信箱，公開的提交紀錄會露出工作單位）。hook 另檢查 `git var GIT_AUTHOR_IDENT` 與 `GIT_COMMITTER_IDENT`，含禁用詞就擋下。
- 用 git hook 守住：禁用詞清單放在 repo 外（`~/.claude/memories`，清單本身也不能公開）。pre-commit 掃要提交的內容，commit-msg 掃提交訊息；比對不分大小寫；英文詞以完整詞比對，詞界也包含識別字裡的分段（例如禁用詞 acme 時，`acmeApi`、`acme_fe` 要擋，`acmes` 這類較長的字不擋），中文詞直接比對字串（`\b` 對中文永遠不成立，用它會讓中文禁用詞全部漏掉），找不到清單就擋下並說明要先建立。hook 放在 repo 的 `.githooks/`，以 `git config core.hooksPath .githooks` 啟用，寫進 README 的安裝步驟。提交前就要擋，因為提交紀錄會留下來。清單與 hook 要在 repo 第一次提交之前建立（目前的文件會進第一個提交）。

## 9. 分階段與內容覆蓋

### 9.1 分階段

每一階段 Debra 審過才進下一階段。每個階段都能單獨上線：`structure.ts` 記著每個主題與實驗的階段，設定裡一個「目前階段」決定哪些已上線；所有畫面都只看已上線的：地圖只列已上線的主題，沒有已上線主題的區與分組整個不顯示；上一個／下一個只在已上線主題之間；實驗連結在實驗上線後才出現。所以不會有連到不存在頁面的卡片或連結，也不做「之後推出」的佔位。實作計畫只把階段 1 寫到逐步，之後各階段先列大綱。

### 9.2 怎麼核對每一段都做進頁面

`docs/content-index.md` 列出全書每一段筆記的去處（主題頁、一行版、不收），給人看；`src/content/sections.ts` 是收錄段落的同一份清單，給程式用。兩者由同一個產生器產生，不手改。

一條鏈從筆記走到畫面：

1. 產生器保證篩選版每一段都進了 `sections.ts`（第 3 節）。
2. 型別保證每個主題都有分組與階段、每段在兩種語言都有一筆文字（第 3 節、6.4）。
3. 一個測試確認已上線主題的每段文字都不是空字串（標題只在沒有書中標題時必填）。
4. 連結檢查確認每個已上線主題都從地圖走得到，頁上每一段都在（6.4）。

產生器本身的檢查見第 3 節。
