## 1. 這課要讓讀者會什麼

**讀者：** 想轉 technical PM 的工程師，或想懂技術的 PM。不需要會寫後端。

**核心問題：** 送出請求後一直沒收到回應，到底成功了沒有？

**學完要能做到（可驗證）：**
1. 說出「逾時」只代表還沒收到回應；從瀏覽器這端看，「請求沒送到」和「已經處理完、只是回應遺失」完全一樣。
2. 寫出逾時時畫面該說什麼，並說明為什麼不能寫「失敗，請重試」。
3. 說明怎樣讓重送不會重複下單：瀏覽器在第一次送出前產生請求 ID，重送沿用同一個 ID，資料庫用唯一約束擋下第二次。
4. 判斷「ID 由伺服器產生」為什麼擋不住（端到端論證）。
5. 把以上寫成一條驗收條件（PM 題）。

**不在這課：** 複製延遲（D2）、兩人同時改（D3）、分散式交易與 2PC、訊息代理的恰好一次。不出題；最後一題下方放「相關主題」連結到 T5、T6、T7 的主題頁（階段 2 起就有），不連到還沒上線的實驗。

## 2. 場景

**一句話：** 使用者在手機訊號不穩時按下「送出訂單」，畫面轉圈後顯示逾時，使用者再按一次。

選「送出訂單」不選後台的「儲存設定」：重複下單＝重複扣款，讀者一看就懂後果。主題頁 T3、T4 的例子也用這個情境，讓主題頁和實驗課用同一套詞。

### 角色（時間軸上的三條線）

| 角色 | 一句話 | 能做的步驟 |
|---|---|---|
| 瀏覽器 | 使用者的手機，送出請求、等回應、顯示畫面 | 送出請求、逾時、顯示結果、使用者重送 |
| 網路 | 只負責送，不保證送到 | 送達請求／弄丟請求／請求晚到（瀏覽器逾時後才送達）；送達回應／弄丟回應／回應晚到 |
| 伺服器與資料庫 | 收到請求就建立訂單並回應 | 處理請求（寫入訂單）、回應 |

網路要獨立成一條線，因為本課的重點就是「網路的命運瀏覽器看不到」。C++ lab 的執行緒線不需要這條，這是主要差異。

### 共用的東西（畫面上的「共用區」）

- **訂單資料表：** 每列一筆訂單，顯示訂單編號與扣款金額。
- **請求紀錄表：** 修復版才出現，每列一個請求 ID，`request_id` 有唯一約束。

### 規則（不變式）

> 使用者想下一張訂單，資料庫裡就只能有一筆；畫面告訴使用者的話必須是真的。

兩個失敗都要能在場景裡做出來：**重複下單**（資料表兩筆）與**畫面說謊**（畫面說失敗，資料庫其實有一筆；或畫面說成功，資料庫其實沒有）。第 1、2 題的「沒有請求 ID」版本，逾時時畫面顯示「送出失敗，請重試」（常見的天真做法）；讀者到第 3 題才選出正確的訊息，之前的畫面不先洩漏答案。從第 4 題起，畫面改用第 3 題的正解訊息，逾時後才到的回應會把畫面改成「訂單已成立」。規則面板隨時檢查兩條：訂單筆數，以及畫面那句話和資料庫是否相符；第 1、2 題裡畫面說了假話時，面板就標出「畫面說謊」。

### 三種程式版本（對應 C++ lab 的 boundary）

| 版本 | 內容 | 用在 |
|---|---|---|
| 沒有請求 ID | 每次 POST 都 `INSERT INTO orders` | 第 1–3、6 題 |
| 伺服器產生 ID | 伺服器收到請求才產生 ID 並寫入請求紀錄表 | 第 5 題 |
| 瀏覽器產生 ID | 瀏覽器第一次送出前產生 ID，重送沿用；伺服器在同一筆交易裡先寫訂單、再 `INSERT INTO requests`（存 `request_id` 與剛產生的 `order_id`）；`request_id` 重複就整筆交易中止（訂單也不留），改查出這個請求 ID 對應的原訂單回傳 | 第 4、6 題 |

### 程式碼面板（取代 C++ 面板）

並排兩塊，跟著目前的步驟反白：

1. **使用者看到的畫面：** 一個手機畫面的示意（按鈕、轉圈、訊息）。這是 PM 讀者真正要看的東西，所以放左邊。
2. **API 與 SQL 片段：** `POST /orders` 的請求內容、伺服器的處理流程、SQL。SQL 從 `examples/order_retry.sql` 切出（同 C++ lab 的 TEACHING-END 規則，SQL 檔裡寫成 `-- TEACHING-END`，只維護一份）。

**可執行的證據（K2）：** C++ lab 用編譯執行的 C++ 當證據；這裡用 Node 內建的 `node:sqlite` 跑 `examples/order_retry.sql`，測試實際執行三種版本的「同一請求處理兩次」，斷言訂單筆數（沒有 ID：2 筆；伺服器產生 ID：2 筆；瀏覽器產生 ID：1 筆，第二次因唯一約束失敗），以及瀏覽器產生 ID 版的重送拿回的是第一筆訂單的 `order_id`。網路的命運只在模型裡模擬，畫面標明「模擬執行」。

## 4. 題目

每題寫明：前提（K1）、讀者要做的推理（K3）、選項各自代表的誤解與回饋（K4、K5）。

### 第 1 題　做出重複下單

- **題目：** 你能排出一個順序，讓使用者只想下一張訂單，資料庫卻有兩筆嗎？
- **操作：** 按各角色的按鈕一步一步跑。「使用者重送」在瀏覽器逾時前是停用的，旁邊寫原因：「還在等回應，使用者看到的是轉圈」。
- **過關條件：** 訂單資料表有 2 筆。所有合法順序都接受，不只標準答案。
- **標準解之一：** 送出 → 網路送達請求 → 伺服器寫入訂單 → 網路弄丟回應 → 瀏覽器逾時 → 使用者重送 → 送達 → 寫入第二筆。
- **回饋：** 由讀者自己的順序產生，點出關鍵那一步，例如「第 4 步網路弄丟的是回應，不是請求；伺服器在第 3 步已經寫入了」；讀者用的是回應晚到或請求晚到時，改說那一步。
- **畫面：** 本題的「沒有請求 ID」版本，逾時時顯示「送出失敗，請重試」，逾時那個請求的回應若逾時後才到，直接忽略（常見的天真做法），所以畫面停在失敗；使用者重送後，重送那次的回應照常顯示「訂單已成立」。規則面板據此判斷畫面是否說謊。

### 第 2 題　同一份程式，重送卻沒事

- **題目：** 不改程式，你能排出一個「第一次請求根本沒到伺服器、使用者也逾時、也重送」，最後只有一筆訂單的順序嗎？
- **過關條件：** 第一次請求遺失、瀏覽器逾時、使用者重送，訂單只有 1 筆。題目已寫明第一次請求沒到，所以所有符合題目的順序都接受。
- **意義：** 讀者自己做出兩個世界：第 1 題是「伺服器處理了，但瀏覽器在逾時前沒收到回應」（回應遺失、晚到，或請求晚到），第 2 題是「請求丟了」。
- **過關後顯示（不出題）：** 兩條時間軸上下並排，只標出瀏覽器那條線看得到的事件，而且只畫到第一次逾時為止（圖說寫明這一點；若讀者第 1 題用了「回應晚到」，之後瀏覽器會多收到一個回應，那會在第 5 節的試跑區看到）。到逾時為止兩條線完全一樣：送出、等待、逾時。說明這就是書上說的「從送出端看，這幾種情況完全一樣」（p.372）。這張圖要能讓讀者自己看出「一樣」，不用靠文字。

### 第 3 題　逾時時畫面該說什麼（預測題，PM 題）

- **前提：** 顯示讀者第 1、2 題的兩條時間軸當參照（固定不動，標注「這兩條不會變，用來檢查你的答案在兩個世界裡是不是都對」）。
- **題目：** 逾時當下，畫面該顯示哪一句？
- **選項與回饋：**
  - 「訂單送出失敗，請重試」：在第 1 題的世界裡是假話，訂單已經成立；而且叫使用者重試，正好造成第 1 題的重複。
  - 「訂單已成立」：在第 2 題的世界裡是假話，請求根本沒送到。
  - 「無法確認訂單是否成立，請到訂單列表查看」：**正解。** 兩個世界都是真話，並且告訴使用者去哪裡確認。但要補一句：如果請求還在路上（請求晚到），列表此刻可能還看不到這筆，使用者照著再下一次仍會重複；畫面誠實只解決「說假話」，真正擋住重複的是第 4 題的請求 ID。
  - 「不顯示錯誤，自動在背景重送」：使用者不會看到假話，但在第 1 題的世界裡一樣會重複下單；畫面誠實不等於資料正確，這要靠第 4 題。
- **揭曉：** 用選到的句子重畫兩個世界，標出哪個世界裡這句話是假的。

### 第 4 題　加上請求 ID，重送會怎樣（預測題）

- **前提：** 程式換成「瀏覽器產生 ID」版。面板顯示改了哪幾行：瀏覽器送出前產生 `request_id`、重送沿用；伺服器先寫入請求紀錄表。
- **題目：** 重播你第 1 題的順序。第二個到達伺服器的請求會發生什麼？（若讀者第 1 題的順序裡，回應在重送之前就晚到了，新版畫面此時已顯示「訂單已成立」，使用者不會再重送；這時改重播標準解，並在題目旁說明原因。）
- **選項與回饋：**
  - 「寫入第二筆訂單」：錯，這次請求帶的是同一個 ID，寫入請求紀錄表時違反唯一約束。
  - 「請求紀錄表擋下，整筆交易中止，伺服器回傳第一筆訂單」：**正解。**
  - 「HTTPS 連線會發現是重複的封包，第二次根本到不了伺服器」：常見誤解。TCP／TLS 只在同一條連線內去除重複的封包；使用者重送是另一個請求、另一筆交易，即使剛好走同一條連線，對 TCP 來說也是新的資料，不是重複的封包（p.587–589）。
  - 「資料庫交易本身就會避免重複」：常見誤解。交易保證一筆請求「全做或全不做」，但兩次送出對資料庫是兩筆不同的交易（p.587–588）。
- **揭曉：** 重畫讀者的順序；共用區的請求紀錄表在第二次寫入時標紅並註明「違反唯一約束」，訂單只有 1 筆。

### 第 5 題　ID 由伺服器產生可以嗎（端到端）

- **題目：** 同事提議：「ID 由伺服器收到請求時產生，前端不用改。」伺服器每收到一個請求就產生一個新的隨機 ID。重播第 1 題的順序，訂單會有幾筆？（書中也提到用表單欄位的雜湊當 ID 可以去重，p.588；本題的前提是隨機 ID，題目要寫明，免得讀者以為是雜湊。）
- **選項：** 1 筆／2 筆／看網路狀況。
- **正解：** 2 筆。伺服器在第二次收到請求時，不知道它和第一次是同一個使用者意圖，於是產生新的 ID。
- **回饋：** 「去重要靠一個從使用者那端一路帶到資料庫的 ID」，這就是書中的端到端論證（p.589）。誤選「看網路狀況」的回饋：「網路狀況決定會不會重送；一旦重送，伺服器產生的 ID 每次都不同，結果固定是 2 筆。」

### 第 6 題　換個情況（transfer，K6）

- **情境：** 改成 App，斷線時會自動重送最多 3 次，使用者沒有按任何東西。模擬區為這題加上「App 自動重送」步驟（逾時後才能按，最多 3 次），取代使用者重送。
- **題目 A：** 沒有請求 ID 時，最多會有幾筆訂單？用瀏覽器產生 ID 版時呢？
  - 正解：最多 4 筆；1 筆。回饋要求讀者在模擬區排出「4 筆」的順序來證明，不能只選數字。要排出 4 筆，前 3 次的回應都得遺失或晚到（第 4 次的回應可以正常送達）；模擬區允許這樣做（試跑區為了精簡才假設重送一定送達，兩者不同要在題目旁寫明）。
- **題目 B（PM 題，開放作答）：** 為「送出訂單」寫一條驗收條件，涵蓋逾時。作答草稿存在瀏覽器本機（讀寫包 try/catch），切換語言或重新整理不會不見。
  - **自評清單（rubric，不比對字句）：** ① 逾時時畫面說「無法確認」並指出去哪裡查 ② 重送沿用同一個請求 ID ③ 伺服器收到重複 ID 時回傳原本的結果，不是錯誤 ④ 只有暫時性錯誤才重送，永久性錯誤不重送（書中的例子是違反約束，p.312；付款被拒是同類的例子）。
  - 讀者勾自己寫到哪幾項。不算分；作答框不是空的才能看參考答案，按鈕停用時旁邊寫原因。

## 5. 全部順序的試跑（第 2 題通過後出現）

規模小，可以全部列出：

- 第一次請求：準時送達／遺失／晚到（瀏覽器逾時後才送達）
- 準時送達時，第一次回應：準時送達／遺失／晚到（晚於逾時）；請求晚到時，回應不影響筆數，合成一列
- 使用者是否重送：是／否（只有逾時後才能重送；重送的請求與回應一律送達，避免爆量；頁面要寫明這個簡化）

共 9 種情況。每格只顯示訂單幾筆，加一句原因。試跑區在第 2 題後出現（第 1、2 題要讀者自己排出順序，試跑表會直接給出答案），也不能提前洩漏後面的答案：不顯示畫面訊息（第 3 題）；「瀏覽器產生 ID」一欄在第 4 題答完後才出現，「伺服器產生 ID」一欄在第 5 題答完後才出現。

| 第一次請求 | 第一次回應 | 重送 | 沒有 ID | 伺服器產生 ID | 瀏覽器產生 ID |
|---|---|---|---|---|---|
| 遺失 | — | 否 | 0 筆 | 0 筆 | 0 筆 |
| 遺失 | — | 是 | 1 筆 | 1 筆 | 1 筆 |
| 準時 | 準時 | 否 | 1 筆 | 1 筆 | 1 筆 |
| 準時 | 遺失 | 否 | 1 筆 | 1 筆 | 1 筆 |
| 準時 | 遺失 | 是 | **2 筆** | **2 筆** | 1 筆 |
| 準時 | 晚到 | 否 | 1 筆 | 1 筆 | 1 筆 |
| 準時 | 晚到 | 是 | **2 筆** | **2 筆** | 1 筆 |
| 晚到 | 任何 | 否 | 1 筆 | 1 筆 | 1 筆 |

回應在逾時後才到的情況（「準時送達、回應晚到」兩列，以及請求晚到的兩列）是第 3 題沒逼讀者想的：逾時後回應才到，畫面要從「無法確認」改成「已成立」。這一點放在第 3 題揭曉之後說明；要不要另出一題，等 Debra 審。
